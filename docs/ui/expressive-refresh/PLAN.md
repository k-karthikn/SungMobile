## Product boundary

SungMobile remains an online YouTube player using the existing catalog, local Likes/playlists/history/sessions, lyrics, queue, appearance and playback settings. Retain the production application ID `com.karthi.sungmobile`, current signing identity, Room data and all present actions. Use `MaterialTheme` roles from `SungTheme` for both light/dark and wallpaper color modes; the screenshots' pale blue and desktop chrome are not literal colors to copy. Keep text readable and use the user's reduced-motion setting and Android animation-scale preference.

Visible screenshot features with no current mobile behavior are excluded: **Local files, audio-output routing, Videos search, arbitrary mood categories, country charts, copied file paths, locating files, audio-reactive visualizer and word-by-word lyric styling**. Do not create decorative placeholder controls for these. The existing “This song's volume” trim (-12 to 0 dB) is the sound control to expose; it does not need an output-device picker.

## Source findings and implementation ownership

- Android already uses `MaterialExpressiveTheme`, `MotionScheme.expressive()`, a snap-based scheme for reduced motion, and a shared `LocalSungMotionEnabled` in `core/designsystem/.../theme/SungTheme.kt`. Do not add a second animation framework or hard-coded animation constants to every screen.
- The desktop Sung source is **reference only**. `qml/MLoadingIndicator.qml` manually draws seven morphing shapes because Qt lacks Compose's rounded-polygon implementation; `qml/CatalogSkeleton.qml` delays placeholders 150 ms to avoid flashes; `qml/LibraryTabs.qml` animates one underline; `qml/MButton.qml`/`qml/Main.qml` use a scalloped play shape and a loading indicator while busy. Recreate the intent using Android Compose APIs, not a port of QML/JavaScript or desktop-only audio levels.
- Build shared visual primitives in `core/designsystem/component` only when feature-neutral: compact app action bar, selectable text tab, expressive loading/status, bounded song row and perhaps a compact playback progress visual. Playback behavior stays in `app/feature/player`; library routing stays in `app/feature/library`; catalog behavior stays in `app/feature/search`.
- `SungApp.kt` remains the single navigation/mini-player owner. Extend its callbacks rather than render another mini-player in Home, Search or Library. Preserve the wide-screen navigation rail and keyboard/inset behavior.
- Keep existing `SungSongListItem` as the base row rather than cloning rows per page. Its flexible trailing slot can accommodate heart, More, selection check and active indicator; if variants grow, add small focused wrappers rather than a giant all-purpose composable.
- Keep queue, search, Room, provider and playback logic outside the visual pass. The new mini-player buttons must call the existing `PlayerActions`/library action paths and respect connected, resolving, buffering, seekable and queue-boundary states.

## Motion and interaction contract

1. Use Material's `MaterialTheme.motionScheme` for selection, tab indicator, button shape/color, menu and content transitions. `animateColorAsState`, `AnimatedContent`/`Crossfade`, and `animateContentSize` are appropriate only when a state actually changes. No endless full-screen decoration.
2. The mini-player's play button is a single visual focal point: resting shape versus soft scalloped/expressive selected shape, with icon change and color following playback state. Show native loading within the control while resolving/buffering. Do not infer audio amplitude from the seek position or add a fake beat visualizer. Accessibility says Play, Pause, Retry or Replay according to the real state.
3. Draw the wavy played segment only while actively playing, with a static filled segment while paused or reduced motion is on. Pause its infinite phase when the app is not resumed. Share geometry or a small draw helper with the full player's `PlayerSeekTrack` where practical; keep accessible progress semantics and a seek action only if the player allows seeking.
4. Underlined Library tab motion follows the selected tab and preserves its state when data loads. Scrolling should reveal the selected tab. Selection tint/check and menu checked state change promptly, with a short color/shape transition. Do not animate each row continuously.
5. Loading appears for real waits (search, source resolution, library/home fetch, lyrics) and disappears when content is ready. An indeterminate indicator does not imply a percent. Keep fixed-size placeholders so image loading does not jump the list. Use a short reveal delay only if testing shows a flash from fast requests.
6. Keep 48 dp minimum touch targets even where the visual nav and icons become smaller; test at increased font scales. Keep text labels or TalkBack descriptions for check-only controls. Honor dark/light, wallpaper palette, reduced motion and Android's disabled animator setting.

## Delivery slices (one page at a time)

1. **Shared shell first:** compact navigation and mini-player in `SungNavigationBar.kt`, `MiniPlayer.kt` and small player-specific helpers. Wire previous/next/More actions through `SungApp.kt`; retain wide-screen rail. Verify that all three destinations show the same player and that pressing transport does not accidentally open Now Playing. Keep the full-player Queue sheet and wavy seek UI unchanged except for shared drawing extraction if needed.
2. **Library:** refine `LibraryHeader.kt` and `LibraryScreen.kt` with text tabs, a compact play/split-action menu, sort/filter layout, direct Recents (existing Recent data) and Mixes (existing mixes + smart playlists). Keep Sessions directly reachable; preserve submenu actions and selection/playlist/cleanup workflows. Home's “Recently played → View all” opens Recents. Add History & privacy inside the existing Settings/Appearance destination before removing its Library More entry.
3. **Home:** reframe only current mixes, recently played, pinned playlists and liked songs. Keep Search, Now Playing and Refresh. Use actual artwork already supplied in local data; no fabricated cards or recommendations.
4. **Search and rows:** text-first selected chips, refined empty/loading/result states, and shared song-row/menu treatment. Keep all four catalog kinds, link handling, pagination, cancellation, retry and provider notices.
5. **Lyrics, loading and remaining settings/menu surfaces:** refine current-line focus/spacing and toolbar; consolidate native loading across Home/Library/Lyrics/mini-player; bring remaining menus and settings into the same surface/typography rules.

Implement slices in focused files and review each with the user before expanding to the next page. Keep backend interfaces stable; if a UI component needs data not in an existing model, stop and map it to a real existing state rather than mock it.

## Verification strategy for the implementation turns

- First, host tests for navigation, Library tab mapping, mini-player callbacks/disabled states, menu actions, Search filter/link behavior, and Lyrics follow/offset behavior where behavior changes. Compile and lint the relevant modules; avoid tests that only assert style implementation details.
- Inspect Compose previews or generated screenshot tests for light/dark, 200% font, narrow phone and wide layout, reduced motion, empty/loading/error, and mini-player playing/paused/buffering. The owner handles real-phone visual/playback acceptance; do not install or run the app on the phone without a specific request.
- Compare scrolling only in an optimized release build, then profile if lag persists. The references alone cannot establish whether artwork decode, composition, network or debug build causes the reported lag. Use stable lazy-list keys/content types and bounded artwork sizes; keep high-frequency playback position reads in the progress subcomponent so the full page does not recompose on each tick.
- Preserve application ID, signer, version-code monotonicity and local data through every release. The current candidate is code 25; any later production APK must use a higher code and a versioned filename.

## Review decisions

Owner-approved navigation direction: **Liked / Playlists / Mixes / Recents / Sessions** inside Library. “Recents” names the existing recently played list clearly; **History & privacy** belongs in Settings, where users can manage recording and clear history. A standalone top-bar clock icon would duplicate the Library destination and crowd the two agreed top actions (Settings and Search). Smart playlists and statistics remain discoverable from Library. The shared mini-player is replaced once, so Home, Search and Library remain consistent. All unsupported screenshot-only features remain excluded.

## Primary Android references

- [Material 3 in Compose](https://developer.android.com/develop/ui/compose/designsystems/material3) and [MotionScheme API](https://developer.android.com/reference/kotlin/androidx/compose/material3/MotionScheme): theme and expressive motion tokens.
- [LoadingIndicator API](https://developer.android.com/reference/kotlin/androidx/compose/material3/LoadingIndicator.composable): native morphing loader available in the project's Material 3 line.
- [Filter chips](https://developer.android.com/develop/ui/compose/components/chip): selection through checkmark and color.
- [Navigation bar](https://developer.android.com/develop/ui/compose/components/navigation-bar) and [Search bar](https://developer.android.com/develop/ui/compose/components/search-bar): destination and search semantics.
- [Compose animation](https://developer.android.com/develop/ui/compose/quick-guides/content/video/animation-in-compose) and [lazy lists](https://developer.android.com/develop/ui/compose/lists): state changes and efficient row reuse.
